If your web application is already in Rails and you need it on iOS and Android, you have three realistic options: build two native apps, build one React Native app, or use Hotwire Native. The third is newer and far less discussed than the other two, so this post is mostly about how it actually performs in production rather than what the launch posts claimed.

What Hotwire Native actually is

Hotwire Native is an open-source framework from the 37signals team behind Rails and Basecamp. It is a native iOS and Android shell that renders your existing Rails views.

There is no JavaScript bundle, no component tree and no second codebase. Your Rails routes map to native screens, your ERB templates render as screens, and Turbo Frames handle navigation. The shell handles the native chrome: navigation bars, tab bars, modals, the app icon, push notifications, app store distribution.

You write Rails. You ship an app.

How it compares on the things that matter

Time to first release

This is where Hotwire Native wins decisively, and it is not a small margin.

A React Native app needs: a React codebase, a Node toolchain, native build configuration for both platforms, a bridge to your Rails API, a design system implemented in React Native components, and someone who can debug a JavaScript error through a native stack trace.

Hotwire Native needs: a native shell (included), your existing Rails app, and a navigation mapping file. The work is in the Rails app you already have.

For MisrPrime I shipped an e-commerce platform where the same Rails controllers and views back both the responsive website and the iOS and Android apps. The mobile-specific work was a navigation config and a handful of view variants — not a second application.

How it feels to use

This is the fair criticism, so let me be precise.

A Hotwire Native screen is a web view. It is fast — you are loading small partials over a local bridge, not full pages — but it is not a native view hierarchy. If you compare a Hotwire Native screen against a pure SwiftUI screen with identical layout, you can see the difference. In practice, for a booking flow, a catalogue, an account area or an admin tool, users do not notice.

What you give up is the ability to use platform-specific widgets that have no web equivalent. A live-activity lock screen widget, a native share sheet with a custom preview, a drag-to-rearrange table with system animations. These are possible via native bridges, but you are back to writing native code, at which point you should ask whether you want two apps.

Push notifications and offline

Push notifications work well — you register for them, get a device token, and hand it to your existing Rails backend. This is a genuine advantage over a lot of hybrid setups, because the notification logic stays in the same codebase as the rest of your application logic.

Offline is the weak point, and I will not pretend otherwise. Hotwire Native does not give you a full offline-first data layer. There is workarounds, and there is a good deal of research still happening in this area. If your product must function fully with no connectivity — a field-service app, an inspection tool, a logistics driver app — plan for that explicitly rather than discovering it late.

The JavaScript question

Hotwire Native uses Hotwire’s JavaScript (Turbo and Stimulus), not React. You get some JavaScript, but it is dramatically less than a React Native app, and none of it is bundled by a Node toolchain.

For a team that is strong in Rails and weak in JavaScript, this is the difference between a project they can ship and a project they cannot.

Long-term maintenance

The maintenance argument favours Hotwire Native strongly, and this is the part most comparisons skip.

With React Native, every dependency you add is a native dependency. A library that has not been updated for two years may not build against the current Xcode or Android Gradle Plugin. You are exposed to the churn of the entire native ecosystem.

With Hotwire Native, the native shell is thin and stable. Most of your application is Rails code, maintained on the Rails release cycle. You are exposed to far less.

That does not mean it is free. You will still deal with App Store review, Xcode version bumps and Android API level changes. But the surface area is much smaller.

When to choose Hotwire Native

Choose it when:

  • Your web app is already in Rails and is good
  • The mobile app is a companion to that web app, not a standalone product
  • You have a small team and need to ship
  • Your team is stronger in Rails than in JavaScript
  • You are extending an existing product rather than starting from scratch

When not to choose it

Choose something else when:

  • You are starting from zero and the app is the product, not a companion
  • You need genuinely native interaction patterns — games, AR, complex gestures, offline-first field work
  • You have an existing React or React Native team and codebase
  • You need deep native integrations (background location, complex Bluetooth, advanced camera work)
  • You need to be in app stores with a fully native-feeling UI benchmarked against the platform’s own apps

The honest summary

Hotwire Native is the right answer more often than its search volume suggests, and the wrong answer less often than its enthusiasts claim. It is a genuinely good fit for “we already have a great Rails app and want it on phones,” which describes a large share of the projects I am asked to build.

It is not a universal replacement for React Native, and any comparison that claims otherwise has not shipped one.

If you have a Rails application and are weighing up mobile, tell me about it — I will give you a straight answer about whether Hotwire Native fits or whether you would be better off elsewhere.
