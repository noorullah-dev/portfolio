A Rails application that is slow at scale is almost never slow because of Ruby. It is slow because of the database.

Ruby executes in the region of a few million simple operations per second. Your application’s response time is spent waiting for PostgreSQL, and the number of round-trips you make dominates everything else you could optimise. Fix the queries and the page gets fast. Micro-optimise the Ruby and nothing visible happens.

This is the order I work in, and it is the order I would recommend.

Step 1: measure before you change anything

Do not guess. Two tools will tell you almost everything you need.

Bullet, by Magician. It wraps N+1 detection, unused eager loading, missing eager loading, and duplicate queries, then prints a visual waterfall when it finds them:

# Gemfile, group :development
gem "bullet"
# config/environments/development.rb
Bullet.enable = true
Bullet.raise = true # fails the request so you cannot ship the N+1

Set Bullet.raise = true in development. It converts a silent N+1 into a failed request, which means it gets fixed rather than forgotten.

Scout or AppSignal, for production. Bullet does not run in production. A slow query that only appears under real data volume needs a real APM to find.

Step 2: the N+1 query

This is the single most common performance defect in Rails, and it is trivially fixable once you recognise it.

You have a list of posts, each belonging to a user:

@posts = Post.all

In your view:

<% @posts.each do |post| %>
  <p><%= post.user.name %></p>
<% end %>

That looks like one query. It is not. Rails runs one query to fetch the posts, then one more for each post’s user. Ten posts means eleven queries. A thousand posts means one thousand and one — and it gets worse with every user you add.

Fix it by telling Active Record what you need:

@posts = Post.includes(:user)

Now it is two queries, always, regardless of list size.

You can also let Bullet find them for you, or look for the tell-tale sign in logs: a query with WHERE "users"."id" = $1 repeated dozens of times.

The subtler version happens through a method call rather than a view. If post.user is called inside a before_action, scope, presenter or serializer, the fix looks the same but the location is harder to find. includes still works.

Step 3: indexes

An unindexed foreign key is a table scan. On a table with 100,000 rows, that is the difference between 2ms and 400ms.

Foreign keys are indexed by default in Rails through references. If you used belongs_to correctly, your foreign keys are already indexed. The ones that are usually missing:

# The slow version: filtered on status, ordered by created_at
Post.where(status: "published").order(created_at: :desc)

# Add a composite index in the right order — equality columns first
add_index :posts, [:status, :created_at]

Column order in a composite index matters enormously. Postgres can use an index for equality conditions on a prefix of the columns, then filter the rest. So [:status, :created_at] serves both “all published posts” and “published posts newest first”. [:created_at, :status] only serves the second.

Check what is actually happening:

EXPLAIN ANALYZE SELECT * FROM posts WHERE status = 'published' ORDER BY created_at DESC;

If you see Seq Scan on a large table, that is your missing index.

Step 4: the query cache

Rails ships a query cache that de-duplicates identical read queries within a single request. It is on by default.

It does not survive across requests, because your data changes between them. For anything read-heavy, cache deliberately.

Rails.cache.fetch("featured_posts", expires_in: 10.minutes) do
  Post.published.includes(:user).limit(10)
end

For read-mostly reference data that changes daily, cache it much longer:

# config/initializers/cache_store.rb — for apps on one server
Rails.cache.configure do |config|
  config.default_cache = :memory_store  # NOT for multi-server: each server gets its own copy
end

If you run more than one application server, use a shared store. Redis or Memcached. An in-memory store on a two-server deployment gives you two different caches, which is a class of bug that only appears in production.

Step 5: stop loading columns you do not use

A model with 80 columns, of which the page needs 6, is transferring 74 columns you are throwing away.

# Only select what the view uses
Post.select(:id, :title, :published_at).includes(:user)

For large text columns this matters a great deal. For most tables, honestly, it does not. Measure before you complicate your code.

Step 6: count efficiently

Model.count on a large table is a full scan unless Postgres can satisfy it from statistics.

# Slow on huge tables
Post.count

# Fast — uses a maintained statistics table
Post.approximate_count(column: :id)

# Or keep an exact cached counter
Post.count_cached

approximate_count uses reltuples and can be slightly stale. For a “1,234 posts” label on a page, that is entirely fine.

Step 7: paginate properly

Model.all with 10,000 rows loads 10,000 rows to render 20.

Post.includes(:user).page(params[:page]).per(25)

The trap is eager loading across a large association. If you eager load posts and their users, then paginate, Postgres still has to join the whole set before limiting. For large datasets, paginate the ids first, then eager load the page:

ids = Post.published.order(created_at: :desc).limit(25).offset(params[:offset]).pluck(:id)
@posts = Post.includes(:user).where(id: ids)

Step 8: fragment and HTTP caching

For markup that is identical for every user, cache the rendered fragment:

<% cache ["sidebar", Sidebar::VERSION] do %>
  <%= render "shared/sidebar" %>
<% end %>

Sidebar::VERSION is a constant you bump when the partial changes. This is the part people get wrong — cached fragments with no version key serve stale content until someone notices and nobody can explain why.

And set real HTTP caching headers. A static asset or a page that is the same for everyone should have a max-age in the tens of minutes or hours, not zero.

What is usually not worth optimising

  • Ruby-level micro-optimisation. Rewriting a loop in a more “efficient” style on a page that spends 400ms waiting on the database changes nothing.
  • Memoising instance variables in views. Saves microseconds, adds coupling, and the readability cost is real.
  • Switching frameworks. If the answer is “it is slow in Rails”, the answer is almost never “it would be faster elsewhere”. It would be equally slow there.

A realistic order of operations

If you inherit a slow Rails application, this is what I do:

  1. Turn on Bullet in development, fix every N+1 it finds
  2. Check EXPLAIN on the five slowest queries from your APM
  3. Add the missing composite indexes
  4. Add caching to the three slowest pages
  5. Check for SELECT * on wide tables
  6. Only then look at anything else

In my experience the first two steps fix 80% of the problem. A Rails application with disciplined queries and correct indexes is fast enough for the overwhelming majority of products.
